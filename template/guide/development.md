## 기획 요약과 개발 시작

다음 입력은 게임 제작 AI가 채팅에서 처리한다. 현재 project_id의 결정·기획서·승인된 목표·실제 작업 기록과 파일을 확인하여 개발 시작 전인지 개발 중인지 판단한다.

### /summary

- 개발 시작 전이면 게임 기획서를 정리한다. 사용자 결정 기록을 바탕으로 장르·핵심 루프·플랫폼과 입력·시점·UI·화풍과 색감·범위와 분량·기술 스택과 에셋 제작 방식·세계관과 스토리·수익모델과 공개 계획·레퍼런스 근거를 담는다. 확정된 내용, 제안 중인 내용, 미결정을 구분한다.
- 기획서는 현재 게임 프로젝트의 문서로 저장하고 사용자에게 내용과 파일 위치를 보여준다. 기존 기획서가 있으면 그 문서를 갱신한다.
- 개발 중이면 승인된 목표에 대한 게임 진척도를 보고한다. 목표, 완료한 부분, 진행 중인 부분, 남은 부분, 막힌 사항과 다음 작업을 실제 작업 기록과 파일에 근거하여 정리한다.
- `/summary`는 정리·보고 요청이다. 개발 시작이나 목표 변경의 승인으로 취급하지 않는다.

### /Development

1. 현재 project_id의 게임 기획서가 반드시 있어야 한다. 기획서가 없으면 저장된 결정으로 먼저 작성하여 보여준다. 개발 목표를 정하는 데 필요한 내용이 미결정이면 기존 질문 규칙에 따라 한 번에 하나씩 묻고 기획서에 반영한다.
2. 기획서를 바탕으로 이번 개발에서 어느 부분까지 완성할지 목표를 보고한다. 구현할 기능, 콘텐츠 종류와 수량, 대상 플랫폼·입력, 완료로 판단할 조건을 구체적으로 적는다.
3. 보고한 기획서와 개발 목표를 대상으로 사용자에게 최종 승인을 요청하고 기다린다. `/Development` 입력 자체는 최종 승인이 아니며, 승인 전에는 게임 구현을 시작하지 않는다.
4. 사용자가 수정을 요구하면 기획서와 목표를 반영하여 다시 제시하고, 수정된 목표에 대한 최종 승인을 받는다.
5. 최종 승인을 받으면 승인 발언과 AI 답변을 기존 사용자 결정 기록 규칙에 따라 보존하고, 승인된 목표 범위의 작업을 시작한다.


## 제작 진행 규칙

### 계획
- 개발 시작 시 사용자가 승인한 SPEC.md를 기준으로 마일스톤을 만든다. SPEC.md에 없는 기능을 임의로 추가하지 않는다. 개수는 정하지 않는다. 마일스톤 하나는 사용자가 화면에서 직접 확인할 수 있는 변화 하나다. 눈에 보이지 않는 작업(구조 정리, 함수 분리 등)은 독립 마일스톤으로 두지 않고 다음 마일스톤에 포함한다.
- 마일스톤 안에서 작업을 어떻게 나눌지는 AI가 정한다. 작업 단위로는 사용자에게 승인받거나 보고하지 않는다. 보고는 마일스톤이 끝날 때만 한다.
- 첫 마일스톤 전에 구조를 한 번 정한다(폴더 구조, 게임 상태 관리, 에셋 불러오는 방식). 작업 결정 기록에 저장하고 이후 마일스톤은 이 구조를 따른다.
- 웹 게임의 기본 스택은 외부 의존성 없는 HTML·CSS·JS이며 빌드 도구를 쓰지 않는다.
- 첫 마일스톤은 에셋 없이 도형·텍스트로 핵심 루프 하나가 동작하는 작은 단위로 한다. 에셋은 마지막 마일스톤에서 교체한다.
- 크기 조절: 연속 두 마일스톤이 수정 없이 통과하면 다음은 더 크게 잡는다(작은 두 개를 합친다). 확인에 실패하거나 막히면 다음은 둘로 나눈다.
- 완료 조건이 서로 다른 동작 둘 이상이면 하나를 끝낼 때 한 줄로 진행만 알리고 멈추지 않는다.
- 계획 전체를 선택지 질문으로 한 번만 승인받는다.
- 마일스톤은 `decisions.py milestone add / set-status / set-progress / list` 명령으로만 기록한다. milestones.json을 직접 편집하지 않는다.

### 마일스톤 루프
1. 시작: STATE.md와 현재 마일스톤, 관련 확정 결정만 읽는다. 전체 기록을 읽지 않는다.
2. 작업: 현재 마일스톤 범위 안에서만 구현한다.
3. 확인: 완료 조건을 1회 확인한다. 통과하면 추가 점검 없이 보고한다. 실패하면 원인을 고치고 해당 항목만 1회 재확인한다. 같은 항목이 연속 2번 실패하면 멈추고 보고한다.
4. 보고: 만든 것, 사용자가 직접 해볼 방법, 막힌 점, 다음 마일스톤을 알리고 멈춘다. 사용자 응답 없이 다음 마일스톤을 시작하지 않는다.
5. 마감: STATE.md를 갱신한다(20줄 이내: 목적, 확정 결정 요약, 현재 마일스톤, 하지 않을 것, 다음 할 일).

### 변경 요청 처리
- 현재 마일스톤 안의 수정은 바로 한다.
- 다른 마일스톤에 속하는 요청은 계획에 추가하고 순서를 묻는다.
- 확정된 결정을 바꾸는 요청은 번복으로 처리한다. 영향받는 작업 결정을 먼저 보여준다.
- 막히면 조건을 바꿔서 해결한 것처럼 보고하지 않는다. 막힌 이유와 선택지를 보고한다.

### 게임 화면 문구 규칙
- 게임 화면(UI, 팝업, 툴팁, 로딩 화면)에는 플레이에 꼭 필요한 문구만 넣는다: 항목 이름, 수치, 버튼 이름, 결과 메시지.
- 규칙 설명, 시스템 안내, 부연 문구("~는 회복되지 않습니다", "~하면 ~됩니다" 같은 설명)는 사용자가 요청한 경우에만 넣는다.
- 사용자가 정하지 않은 규칙(예: 훈련하면 체력이 회복되는지)을 구현하면서 정해야 할 때는 가장 단순한 쪽으로 구현하고, 그 결정을 화면에 설명하지 않는다. 마일스톤 보고에 결정 내용을 적고 사용자에게 묻는다. 되돌리기 비싼 결정이면 작업 결정 기록에 저장한다.
- 화면 문구는 모두 한 파일(texts.js)에 모아 두고 코드에 문장을 직접 쓰지 않는다. 마일스톤 보고에는 이번에 추가하거나 바꾼 문구 목록을 적는다.
- 장식용 문구(슬로건, 소개 문장, 단계 안내)도 요청 없이 추가하지 않는다.
