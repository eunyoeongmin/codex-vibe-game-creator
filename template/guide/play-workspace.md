# 플레이 작업 공간과 시스템 연결도

현재 배정받은 작업의 절만 읽는다. Python과 decisions.py는 AGENTS.md의 프로젝트 경로를 쓴다. 등록·지점·관찰은 data/creator.sqlite에 보존한다. 사용자 결정과 작업 결정의 역할을 대체하지 않는다.

## 연결 작업

실제 게임의 대상, 시스템, 스테이지·이벤트·보상·해금을 등록한다. 게임에 없는 기능을 연결도 채우기용으로 만들지 않는다. 시스템 전체를 매번 다시 조사하지 않고 요청한 대상과 연결된 기존 처리만 확인한다. 스토리 창작은 독립 스토리 담당의 작업이며 이 등록 작업에 포함하지 않는다.

1. 현재 코드의 진입점, 읽고 바꾸는 상태, 실행 조건과 결과를 확인한다. 기존 결정·에셋·데이터와 연결할 때 `relation list`가 반환하는 노드 id를 refs로 사용한다. ID를 임의로 꾸미지 않는다.
2. 아래 형식의 입력을 프로젝트 안 파일로 만들고 `live register --input <파일>`로 등록한다. 재등록에는 현재 revision을 `--revision`으로 전달한다. 생성되는 content/creator-systems.json은 직접 편집하지 않는다.
3. `live runtime`으로 game-tools/live-runtime.js를 배치하고 게임에서 불러온다. 게임 초기화 후 `GameCreatorLive.load('content/creator-systems.json', options)`를 호출한다. 하위 경로 HTML이면 URL을 맞춘다. 기존 상태 소유자·게임 루프를 재사용한다.
4. 실제 연결이 실행된 지점에서 `GameCreatorLive.emit(edgeId, values)`를 호출한다. 설계에 있다는 이유로 실행 기록을 만들어 넣지 않는다. values는 해당 동작의 작은 JSON 객체이며 원문 대화나 전체 게임 상태를 반복해서 넣지 않는다. 기록 버튼을 누르기 전에는 수집하지 않고 최근 120건만 유지한다.

등록 입력:
- entry: 실제 게임 HTML의 프로젝트 상대 경로.
- nodes: `{id,name,kind,role,reads:[],writes:[],refs:[],evidence:[]}` 배열. kind는 system/entity/stage/event/reward/unlock 중 하나다. role은 해당 게임에서의 역할이다. reads와 writes는 실제 상태 이름이다.
- edges: `{id,source,target,trigger,condition,effect,status,refs:[],evidence:[]}` 배열. source/target은 node ID, trigger는 발생 동작, condition은 조건, effect는 결과다. status는 planned/implemented다. implemented에는 현재 코드 근거가 필요하다. 근거만으로 플레이에서 실행됐다고 말하지 않는다.
- targets: `{id,name,node_ids:[],selector,refs:[]}` 배열. node_ids는 이 화면 대상과 연결된 시스템·콘텐츠다. DOM 대상은 기존 요소의 selector, Canvas 대상은 빈 selector와 아래 pick 어댑터를 사용한다.
- evidence 항목: `{path,quote}`. 실제 게임 파일의 상대 경로와 그 파일에 존재하는 정확한 인용이다. 등록 시 해시를 보존하며 파일 변경 후에는 오래된 근거로 표시한다.
- ID는 영문·숫자·밑줄·마침표·콜론·하이픈으로 1~100자다. 노드와 연결 ID는 서로도 중복하지 않는다.

설계안만 있는 연결은 planned로 등록한다. 스테이지→이벤트→보상→해금처럼 실제 게임에 있는 콘텐츠 흐름도 같은 노드·연결 형식으로 표현한다. 기획 자료와 실제 사용하는 콘텐츠 행을 refs로 연결하고, 미정 조건·수치를 확정된 규칙으로 바꾸지 않는다.

## 화면 대상과 상태 연결

options.pick({x,y,width,height})은 미리보기 뷰포트 CSS 좌표에서 게임의 카메라·배율·Canvas 위치를 반영해 등록된 target ID 또는 null을 반환한다. 기존 엔진의 히트 테스트를 사용한다. 임의의 클릭 좌표를 특정 게임 객체라고 단정하지 않는다. DOM selector만으로 선택할 수 있으면 pick을 추가할 필요가 없다.

options.pause와 options.resume은 함께 제공한다. 기존 루프·타이머·입력의 중복 시작을 막고 게임이 실제로 멈추고 재개되도록 연결한다. 일시 정지가 없으면 대시보드가 이를 표시하며 순간 상태만 저장한다.

같은 지점에서 비교하려면 guide/gameplay-tools.md의 ‘플레이 저장과 실행 지점’ 절에 따라 GameCreatorPlay를 실제 게임에 연결한다. 날짜·퀘스트·장비·카메라 등 해당 구간의 상태와 난수 시드·게임 시계·예약된 동작을 필요한 범위에서 저장·복원한다. 일시 정지 같은 대시보드 제어 상태는 게임 진행 상태와 분리한다. 어댑터 등록만으로 같은 결과가 재현된다고 보고하지 않는다.

## 저장 지점의 수정 요청

대시보드는 선택 대상, 주변 시스템·연결, 관련 결정·에셋·콘텐츠 기록, 실제 관찰된 동작, 캡처 상태를 요청에 첨부한다. 관련 없는 전체 기록을 추가로 읽지 않는다. runtime 기록에 없는 동작은 미관찰이며 미구현 판정이 아니다. 코드 근거가 오래됐으면 해당 부분만 다시 확인한다.

`live graph`, `live points`, `live point <ID>`로 등록과 저장 지점을 조회할 수 있다. 지점을 저장한 뒤 게임 파일이 바뀌면 기존 상태로 새 수정안을 만드는 요청을 거부한다. 미리보기를 다시 열고 새 지점을 저장한다. 등록·코드 변경 뒤 실행 중인 화면을 최신 상태라고 간주하지 않는다.

## 원본과 수정안

대시보드는 저장 지점의 원본 파일로 비교안을 만든다. live_variant 요청의 folder 안만 수정한다. 원본·확정 결정·SPEC·마일스톤·content/creator-systems.json은 수정하지 않는다. 전달된 상태 형식과 등록 ID를 유지하고 지정된 차이만 구현한다. 비교안 폴더에서는 원본 프로젝트 DB를 수정하는 명령을 실행하지 않는다.

대시보드가 원본과 수정안의 게임을 별도로 열고 저장 상태를 양쪽에 복원한다. 상태가 비호환이면 채택에 앞서 해당 복원 문제를 해결한다. 사용자가 직접 비교하고 원본 유지 또는 수정안 채택을 고른다. 원본은 채택 전에 체크포인트로 보존하며 탈락 파일은 자동 삭제하지 않는다. 사용자 선택은 지점 기록에 남는다. 채택 후 변경된 코드 근거와 연결이 있으면 그 부분을 재등록한다. 재미·취향·완성도에 대한 사용자 승인을 AI가 대신하지 않는다.

## 담당별 수행 범위

- 오케스트레이터: 사용자 요청과 캡처 문맥, 변경 범위를 담당에게 전달한다. 연결 작업이면 담당에게 이 문서의 해당 절 경로를 넘긴다. 하위 담당의 실무를 중복 수행하지 않는다.
- 게임 디자이너: 기존 결정에 맞는 시스템·콘텐츠 연결과 미정 설계 가설을 구분한다. 수량 확정이 세부 내용 승인이라는 뜻은 아니다.
- 개발 담당: 실제 코드·대상·상태 어댑터와 emit을 연결하고 변경된 등록을 갱신한다. 빈 등록만으로 연결 완료라고 보고하지 않는다.
- 검증 담당: 변경된 경로에서 선택·상태 복원·해당 연결 실행을 필요한 범위로 확인한다. 전체 그래프의 모든 연결을 재검사하지 않는다. 화면 대상·연출은 실제 화면에서 확인하며 데이터 조회만으로 시각적 결과를 통과시키지 않는다.
