# 게임 코드 구조 기준

## 적용 범위

- 열람 시점·절과 재조회 조건은 AGENTS.md의 ‘문서 읽기 원칙’과 ‘상황별 필독 문서’를 따른다. 이 문서의 원칙을 지키는 것과 매 수정마다 전체 본문을 다시 읽는 것은 별개다.
- 이 문서는 구현할 기능 목록이 아니다. 승인된 게임에 필요한 구조만 적용한다. 저장 기능이 없는 게임에 저장 시스템을 만들거나, 다국어 지원 요청 없이 번역·언어 선택 화면을 추가하지 않는다.
- 기존 엔진과 승인된 프로젝트 구조를 먼저 따른다. 엔진이 제공하는 상태·입력·리소스·번역 기능을 별도 자체 시스템으로 중복 구현하지 않는다.
- 파일 수·줄 수·클래스 수를 품질 기준으로 삼지 않는다. 작은 게임은 적은 파일과 단순한 함수로 구성할 수 있다. 폴더를 나누는 것보다 상태의 소유자, 변경 경로, 기능 사이의 호출 관계가 명확해야 한다. 예상만으로 범용 프레임워크나 추상 계층을 만들지 않는다.
- 기존 구조를 전부 다시 쓰거나 관련 없는 부분을 정리하지 않는다. 이번 구현을 막는 구조 문제가 있다면 위치·영향·필요한 변경을 오케스트레이터에게 반환한다. 구조 정리 자체를 별도 마일스톤이나 새 목표로 만들지 않는다.

## 구조 결정과 유지

- 첫 마일스톤 전에 폴더 구조, 게임 상태 관리, 에셋을 불러오는 방식을 한 번 정해 작업 결정에 저장한다. 이후에는 그 구조를 따르며 바꿀 때는 근거와 영향을 기록한다.
- 기능을 추가하기 전에 기존 상태의 소유 위치, 관련 규칙의 처리 함수, 입력에서 화면 반영까지 이어지는 경로를 찾는다. 기존 처리 위치가 있으면 그 경로를 사용한다. 연결 관계를 조사할 때는 [기존 시스템 연결 조회](workbench.md#기존-시스템-연결-조회), 실제 선택을 저장할 때는 [작업 결정 기록](work-decisions.md)의 해당 절을 확인한다.
- 폴더별 책임, 주요 진입점, 중요한 상태의 소유 위치와 호출 방향을 짧게 남긴다. 프로젝트의 기존 구조 문서가 있으면 그곳을 갱신하고 동일한 설명을 다른 문서에 복제하지 않는다. 없으면 프로젝트의 `ARCHITECTURE.md`에 정리한다. 코드 변경으로 달라진 부분만 함께 갱신한다.
- 이름은 역할과 의미가 드러나게 쓴다. 주석에는 코드로 바로 알 수 있는 동작을 반복하지 않고 선택 이유·제약·예외 이유를 남긴다. 코드와 다른 오래된 설명을 남기지 않는다.

## 기능별 기준

| 원칙 | 적용되는 상황 | 피해야 할 예시 |
|---|---|---|
| 상태의 소유 위치와 변경 경로를 정한다. 화면용 복사 값은 원본에서 계산한다. | 체력·날짜·소지품 등 여러 기능에서 사용하는 상태가 있을 때 | 화면과 전투 코드가 각각 별도의 체력을 직접 갱신함 |
| 같은 의미의 규칙은 공통 처리를 호출한다. 이름이나 모양이 비슷하다는 이유만으로 서로 다른 규칙을 합치지는 않는다. | 여러 행동이 같은 결과나 규칙을 공유할 때 | 훈련·수면·이벤트마다 날짜 변경과 일일 갱신 코드를 복사함 |
| 입력을 게임 행동으로 변환하고 규칙은 그 행동을 처리한다. 승인된 입력 방식만 구현한다. | 키·버튼·터치 등으로 같은 행동을 실행할 때 | 키보드 핸들러와 터치 핸들러에 피해 계산을 각각 구현함 |
| 규칙 처리와 화면 표시의 책임을 구분한다. 그리기·화면 갱신이 게임 상태 변경의 원인이 되지 않게 한다. | UI·캔버스·장면이 게임 상태를 표시할 때 | 화면을 다시 그릴 때 보상을 지급하거나 피해를 계산함 |
| 반복되는 콘텐츠의 구성·수치는 안정적인 ID를 가진 데이터로 두고 공통 로직이 읽는다. 고유 동작까지 억지로 데이터화하지 않는다. | 아이템·적·스테이지 등 같은 종류의 콘텐츠가 늘어날 때 | 적 하나를 추가할 때마다 같은 로직을 복사하고 여러 곳에 이름별 조건문을 붙임 |
| 시간·상태 변경·후속 이벤트의 처리 순서와 재진입 조건을 명확히 한다. | 한 행동이 여러 시스템의 갱신을 일으킬 때 | 같은 보상이 중복 지급되거나 구독 순서에 따라 하루 갱신 결과가 달라짐 |
| 생성한 타이머·입력 처리·이벤트 구독·리소스는 수명을 소유하는 위치에서 해제한다. | 화면 전환, 전투 종료, 재시작, 객체 제거가 있을 때 | 재시작할수록 입력 핸들러가 쌓여 공격이 여러 번 실행됨 |
| 저장할 상태를 실행 중 객체와 분리하고 저장 형식에 버전을 둔다. 형식 변경 시 기존 데이터의 호환 처리와 실패 동작을 정한다. | 저장·불러오기 기능을 구현하거나 저장 구조를 바꿀 때 | 화면 객체·오디오 객체를 그대로 저장하거나 읽지 못한 저장 파일을 조용히 초기화함 |
| 에셋 ID와 경로·불러오기 방식을 정해진 위치에서 관리한다. 제작 이력·확정 여부는 기존 에셋 기록으로 관리한다. | 여러 위치에서 같은 이미지·사운드 등을 참조할 때 | 같은 파일 경로가 여러 코드에 흩어져 교체 후 일부 화면만 옛 파일을 사용함 |
| 모듈의 공개 함수·데이터 경계를 정하고 호출 방향을 유지한다. | 기능을 여러 모듈로 나누거나 기존 모듈을 연결할 때 | 서로의 내부 변수를 직접 수정하거나 순환 호출로 상태 변경을 추적할 수 없게 만듦 |

## 문구와 다국어 대응

- 게임 로직의 ID·상태값과 사용자에게 보여주는 이름·문장을 구분한다. 표시 이름이나 번역문을 분기 조건·저장 식별자로 사용하지 않는다.
- 사용자에게 보이는 문구는 정해진 문구 저장 위치에서 관리하고 코드에서는 문구 키와 필요한 값을 전달한다. UI·팝업·툴팁·로딩·캔버스 글자·사용자용 오류·접근성 문구도 같은 기준을 적용한다. 개발자용 로그를 플레이어용 문구로 노출하지 않는다.
- 문장은 문구 데이터에 완성된 단위로 두고 코드에서는 `{amount}` 같은 값만 전달한다. 코드에서 단어를 이어 붙이거나 언어별 문장·어순 분기를 여러 기능에 흩어 놓지 않는다. 지원 언어에서 필요한 복수형·날짜·숫자 표기는 선택한 문구 처리 방식의 한 곳에서 처리한다.
- 문구 표와 콘텐츠 데이터를 구분한다. 아이템 데이터에는 ID·공격력·가격·문구 키를 두고, 문구 표에는 해당 키의 이름·설명과 필요한 언어별 표현을 둔다. 게임의 모든 데이터를 한 번역 표에 모으지 않는다.
- CSV·JSON·JavaScript 문구 모듈·엔진의 번역 리소스 중 기존 스택과 규모에 맞는 형식을 선택한다. 특정 파일명이나 형식을 강제하지 않는다. 원본에서 실행용 파일을 생성한다면 편집할 원본을 하나로 정하고 생성물을 따로 수정하지 않는다. 변환을 위해 불필요한 빌드 체계를 도입하지 않는다.
- 지원 언어는 사용자가 정한 범위만 구현한다. 단일 언어에서도 문구 키와 표시 문자열은 분리하되, 번역·언어 선택 기능은 요구된 때 추가한다. 번역을 바꾸기 위해 게임 규칙 코드를 수정할 필요가 없어야 한다.
- 사용자 입력, 결정 기록의 사용자 원문·AI 답변 원문은 번역용 문구와 구분하고 덮어쓰지 않는다. 문구 분리는 새로운 설명·표시를 추가할 근거가 아니다. 넣을 정보와 표현의 범위는 승인된 설계 및 개발 담당의 화면 문구 규칙을 따른다.

## 변경 범위의 구조 확인

검증 담당은 이번에 바뀐 책임과 연결을 대상으로 해당 기준의 위반 여부를 확인한다. 기준 전체를 매번 실행하는 체크리스트로 쓰지 않는다. 구조 확인은 코드·데이터 참조로 수행할 수 있지만, 실제 동작·화면 검증의 대체 근거가 아니다. 범위·실행·반복 한도는 검증 담당 지침을 따른다.

- 새 상태·규칙이 기존 것과 중복되거나 공통 처리 경로를 우회했는지 확인한다.
- 입력 → 규칙 처리 → 상태 변경 → 화면 반영의 경로를 추적할 수 있는지, 관계없는 모듈의 내부 변경에 의존하는지 확인한다.
- 문구·콘텐츠·에셋을 바꾸는 작업이 규칙 코드 변경을 요구하게 되었는지 확인한다. 새 문구 키가 실제 문구 데이터에 존재하고 값 치환에 필요한 항목이 맞는지, 언어별 문장이 코드에 직접 들어갔는지 확인한다.
- 폴더 수나 선호하는 패턴과 다르다는 이유로 실패시키지 않는다. 위반을 보고할 때는 기준, 해당 코드·데이터 위치, 이번 변경에 미치는 영향을 함께 적는다. 직접 영향이 없는 기존 문제를 전체 리팩터링 과제로 확대하지 않는다.
