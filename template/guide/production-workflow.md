# 제작 진행 절차

이 문서는 메인 챗의 오케스트레이터가 따르는 진행 절차다. 사용자와의 소통, 작업 배분, 마일스톤 상태와 STATE.md의 최종 갱신을 맡는다. 게임디자인·개발·아트·검증 담당은 맡은 범위의 결과를 오케스트레이터에게 반환한다.

## 역할과 전달 원칙

- AGENTS.md의 담당별 표에서 작업에 맞는 담당과 지침 경로를 골라 전달한다. 오케스트레이터가 담당 지침을 먼저 읽고 수행 방법을 재작성하지 않는다. 해당 담당이 자기 지침을 직접 읽는다. 모든 담당에게 모든 문서와 대화 기록을 일괄 전달하지 않는다.
- 게임 규칙·콘텐츠·수치와 기존 시스템 연결 설계는 게임 디자이너에게 관련 사용자 결정과 판단을 맡긴 범위를 전달해 맡긴다. 새로운 사용자 선택이 필요한 사항을 반환받으면 기존 결정 절차로 연결한다. 개발 담당이 구현 편의를 위해 대신 확정하지 않는다.
- 스토리·세계관·서사 구조의 결정과 제작은 별도 작업이다. 게임디자인·개발·아트 작업에 포함시키지 않는다. 필요하면 사용자에게 범위와 방향을 확인한다. 이미 승인된 내용을 구현에 사용하는 것과 새로 창작하는 것을 구분한다.
- 역할 수만큼 항상 에이전트를 실행하지 않는다. 해당 작업에 필요한 담당만 선택한다. 실행 환경에 실제 위임 기능이 없으면 위임했다고 보고하지 않는다.
- 전달할 내용: 이번 목표와 완료 조건, 관련 SPEC.md 버전·결정 ID·에셋 ID, 읽을 지침, 현재 상태, 수정 가능한 파일·범위, 범위 밖 사항, 반환할 결과. 재검증이면 기존 실행 결과와 횟수도 전달한다.
- 같은 파일이나 진행 기록의 작성 담당을 명확히 지정한다. 여러 담당이 같은 기록을 서로 덮어쓰게 하지 않는다.
- 담당자는 사용자에게 독립적으로 승인 질문을 보내거나 목표를 바꾸지 않는다. 필요한 결정을 오케스트레이터에게 전달하고 영향을 받는 부분만 보류한다.
- 수량 확정은 AI가 구성한 개별 결과물의 승인까지 포함하지 않는다. 작업 기록의 active, 구현 완료, 검증 통과, 사용자 승인은 서로 구분한다.
- 레퍼런스 조사가 필요하면 레퍼런스 담당에게 맡기고, 실제 확인한 자료·사용자 선택·해석을 받아 사용자에게 보여준다. 설계 담당에게 해당 근거 ID를 전달하고 적용 계획과 실제 적용 위치를 반환받는다. 검색했다는 진행 보고만으로 결과 설명을 대신하지 않는다.

## 기획 요약과 개발 시작

현재 project_id의 결정·기획서·승인된 목표·실제 작업 기록과 파일을 확인하여 개발 시작 전인지 개발 중인지 판단한다.

### /summary

- 개발 시작 전이면 게임 기획서를 정리한다. 사용자 결정 기록을 바탕으로 장르·핵심 루프·플랫폼과 입력·시점·UI·화풍과 색감·범위와 분량·기술 스택과 에셋 제작 방식·세계관과 스토리·수익모델과 공개 계획·레퍼런스 근거를 담는다. 확정된 내용, 제안 중인 내용, 미결정을 구분한다.
- 기획서는 현재 게임 프로젝트의 문서로 저장하고 사용자에게 내용과 파일 위치를 보여준다. 기존 기획서가 있으면 그 문서를 갱신한다.
- 개발 중이면 승인된 목표에 대한 게임 진척도를 보고한다. 목표, 완료한 부분, 진행 중인 부분, 남은 부분, 막힌 사항과 다음 작업을 실제 작업 기록과 파일에 근거하여 정리한다.
- `/summary`는 정리·보고 요청이다. 개발 시작이나 목표 변경의 승인으로 취급하지 않는다.

### /Development

1. 현재 project_id의 게임 기획서가 반드시 있어야 한다. 기획서가 없으면 저장된 결정으로 먼저 작성하여 보여준다. 개발 목표를 정하는 데 필요한 내용이 미결정이면 기존 질문 규칙에 따라 한 번에 하나씩 묻고 기획서에 반영한다.
2. 기획서를 바탕으로 이번 개발에서 어느 부분까지 완성할지 목표를 보고한다. 구현할 기능, 콘텐츠 종류와 수량, 대상 플랫폼·입력, 완료로 판단할 조건을 구체적으로 적는다.
3. 보고한 기획서와 개발 목표를 대상으로 사용자에게 최종 승인을 요청하고 기다린다. `/Development` 입력 자체는 최종 승인이 아니며, 승인 전에는 게임 구현을 시작하지 않는다.
4. 사용자가 수정을 요구하면 기획서와 목표를 반영하여 다시 제시하고, 수정된 목표에 대한 최종 승인을 받는다.
5. 최종 승인을 받으면 승인 발언과 AI 답변을 기존 사용자 결정 기록 규칙에 따라 보존하고, 승인된 목표 범위의 작업을 시작한다.

대시보드에서는 요약 카드가 SPEC.md 승인과 저장을 처리한다. 서버의 승인 메시지를 받으면 같은 기획서 승인을 다시 묻지 않고 아래 계획 단계로 넘어간다. 대시보드의 기록·저장 결과를 확인하지 않은 채 승인이나 SPEC.md 생성을 대신했다고 간주하지 않는다.


## 제작 진행 규칙

### 계획
- 개발 시작 시 사용자가 승인한 SPEC.md를 기준으로 마일스톤을 만든다. SPEC.md에 없는 기능을 임의로 추가하지 않는다. 개수는 정하지 않는다. 마일스톤 하나는 사용자가 화면에서 직접 확인할 수 있는 변화 하나다. 눈에 보이지 않는 작업(구조 정리, 함수 분리 등)은 독립 마일스톤으로 두지 않고 다음 마일스톤에 포함한다.
- 마일스톤의 구현 작업 분할은 개발 담당에게 맡긴다. 작업 단위로 사용자에게 승인받거나 보고하지 않는다. 사용자에게는 마일스톤이 끝날 때 보고한다.
- 첫 마일스톤은 에셋 없이 도형·텍스트로 핵심 루프 하나가 동작하는 작은 단위로 한다. 에셋은 마지막 마일스톤에서 교체한다.
- 크기 조절: 연속 두 마일스톤이 수정 없이 통과하면 다음은 더 크게 잡는다(작은 두 개를 합친다). 확인에 실패하거나 막히면 다음은 둘로 나눈다.
- 계획 전체를 선택지 질문으로 한 번만 승인받는다.
- 마일스톤은 `decisions.py milestone add / set-status / set-progress / list` 명령으로만 기록한다. milestones.json을 직접 편집하지 않는다.

### 마일스톤 루프
에셋이 관련된 마일스톤과 최종 완료 보고 전에는 아트 담당에게 임시·제안 에셋과 남은 교체 사항을 확인해 반환하도록 요청한다. 사용자 선택이 필요한 항목은 그 결과를 바탕으로 제시한다.

1. 시작: STATE.md와 현재 마일스톤, 관련 확정 결정을 읽는다. 전체 기록을 읽지 않는다. `decisions.py milestone set-status <id> active`로 시작을 기록하고 목표·담당·수정 범위를 전달한다.
2. 작업: 개발 담당에게 현재 마일스톤 범위 안의 구현을 맡기고, 필요한 아트·게임디자인 작업을 구분해 연결한다. 진행도 기록 담당자를 지정하고 작업 결과와 진행 상황을 받는다.
3. 확인: 구현 결과·변경 위치·이미 수행한 검사와 횟수를 검증 담당에게 전달한다. 검증 담당이 자기 지침에 따라 범위·반복·중단을 판단하고 결과와 필요한 결정을 반환한다. 사용자 지시가 필요한 사항은 사용자에게 확인해 전달한다. 실패 항목의 수정은 개발 담당에게 돌려보낸다. 완료 조건을 통과하면 `set-status <id> done`, 막혀 중단하면 `set-status <id> blocked`로 기록한다. 구현 작업 수가 total에 도달했다는 이유만으로 done으로 바꾸지 않는다.
4. 보고: 만든 것, 사용자가 직접 해볼 방법, 막힌 점, 다음 마일스톤을 알리고 멈춘다. 사용자 응답 없이 다음 마일스톤을 시작하지 않는다.
5. 마감: 오케스트레이터가 담당들의 결과를 모아 STATE.md를 갱신한다(20줄 이내: 목적, 확정 결정 요약, 현재 마일스톤, 하지 않을 것, 다음 할 일). 위임 전에도 다음 할 일과 담당 범위를 현재 상태로 맞춘다.

### 변경 요청 처리
- 현재 마일스톤 안의 수정은 해당 담당에게 바로 전달한다.
- 다른 마일스톤에 속하는 요청은 계획에 추가하고 순서를 묻는다.
- 확정된 결정을 바꾸는 요청은 번복으로 처리한다. 영향받는 작업 결정을 먼저 보여준다.
- 막히면 조건을 바꿔서 해결한 것처럼 보고하지 않는다. 막힌 이유와 선택지를 보고한다.
