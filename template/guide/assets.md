# 에셋 관리

## 기준과 역할

- 이미지와 사운드를 관리한다. 코드로 그린 도형·이펙트·UI 장식과 코드로 합성한 소리도 에셋이다. 별도 이미지나 음원 파일이 없으면 구현 코드 경로와 함수·선택자 등 위치를 기록한다.
- 에셋을 만들거나 바꾸기 전에 해당 용도의 기존 에셋과 관련 confirmed 아트 결정·레퍼런스를 조회한다. 사용자 결정의 원본은 user_decisions이며 에셋별 제작 메모로 덮어쓰지 않는다.
- 용도와 하위 분류는 게임에 맞게 자유롭게 작성한다. 캐릭터·전투·배경 같은 특정 게임의 분류를 필수 목록으로 만들지 않는다.
- 이 문서는 에셋을 직접 제작·관리·적용하는 담당이 사용하는 공통 규칙이다. 다른 담당의 역할 지침을 추가로 읽도록 요구하지 않는다. 아트 담당은 제작·관리, 검증 담당은 실제 화면 배치·조작·표시 오류 확인, 개발 담당은 게임 코드의 적용을 맡는다.

## 제작과 교체

1. 오케스트레이터가 개발 담당의 구현 요구를 포함해 필요한 결과물, 사용 상황, 구현에 필요한 크기·형식·상태·동작을 전달한다. 기존 결정에서 찾을 수 있는 사항은 사용자에게 다시 묻지 않는다.
2. 공통 아트 기준은 관련 user_decisions의 ID로 연결한다. 에셋별 비례·색·선·명암·시점·해상도·프레임·투명 배경 등 실제 필요한 제작 조건은 art_notes에 적는다. 사운드는 길이·반복·악기나 음색·강도 등 해당 요청에 필요한 조건을 적는다. 정하지 않은 항목을 일괄적으로 추가하지 않는다.
3. 제작 방식을 methods에 기록한다. 코드와 생성 이미지를 섞는 등 복수 방식이면 각 부분을 어느 방식으로 만드는지와 혼합 이유를 reason/source_note에 적는다. 혼합 자체를 금지하지 않으며, 임시 구현을 최종 방식으로 취급하지 않는다.
4. 초반 구현을 위해 만든 결과물은 temporary로 등록하고 replacement_plan에 무엇을 언제 어떤 기준으로 교체할지 적는다. 미정인 제작 방향은 미정임을 기록하고 최종 선택으로 단정하지 않는다.
5. 결과물을 만들면 파일 경로와 실제 적용 상태를 갱신한다. 게임에서 쓰고 있다는 이유나 마일스톤이 끝났다는 이유로 confirmed로 바꾸지 않는다. 사용자에게 제시한 후보는 proposed, 사용자가 선택한 결과만 confirmed로 기록하고 승인 원문을 남긴다.
6. 승인된 에셋의 파일·표현 방식·아트 조건을 바꿀 때 기존 승인을 재사용하지 않는다. 새 결과는 proposed로 기록하고 승인을 받는다. 사용자가 직접 교체 결과를 선택했다면 그 원문으로 확정할 수 있다.
7. 확정본을 수정할 때는 별도 경로로 새 파일을 만들고 에셋 ID는 유지하여 update한다. 기록 이력은 당시 경로와 설명을 보존하지만 파일 자체의 백업은 하지 않는다. 같은 경로의 원본을 덮어써서 과거 결과를 잃지 않는다.
8. 사용자가 거절한 결과물은 보관·삭제 의사를 확인한다. retired는 사용 종료 표시일 뿐 파일 삭제가 아니다. 다른 에셋이나 코드가 공유하는 파일은 그 사용 관계도 확인한 후 사용자가 승인한 파일만 처리한다.

## 임시 에셋이 남지 않도록 확인하는 시점

- 관련 마일스톤을 시작할 때 해당 용도의 에셋을 조회하고, 끝날 때 files와 usage_state를 실제 적용 상태에 맞게 갱신한다.
- 에셋 교체 단계와 최종 제작 완료 보고 전에는 temporary 및 proposed 목록을 조회한다. 사용 중인 임시 에셋의 유지·교체 여부와 이유를 사용자에게 제시한다. 임시물을 남겨 둔 상태에서 최종 아트 교체까지 끝났다고 보고하지 않는다.
- 사용자가 임시 표현을 그대로 최종 결과로 선택하면 승인 원문과 유지 이유를 남기고 confirmed로 바꾼다. 이전의 임시 상태와 교체 계획은 이력에 보존한다.
- 연결된 아트 결정이 번복되면 해당 ID를 참조하는 에셋을 찾아 영향과 수정 필요 여부를 오케스트레이터에게 전달한다. 기존 에셋을 자동으로 재생성하지 않는다.
- 기존 프로젝트의 파일만 보고 제작 방식·승인 여부·용도를 추측해 등록하지 않는다. 코드와 제작 기록에서 확인 가능한 사실을 정리하고, 기록이 없는 결과는 confirmed로 만들지 않는다.

## 저장 항목

프로젝트의 data/decisions.sqlite에 assets와 asset_revisions로 저장한다. 이미지·사운드 파일 자체는 DB에 넣지 않는다. 명령은 .project 마커가 있는 프로젝트 안에서 실행한다.

| 필드 | 내용 |
|---|---|
| id / revision | A-001부터 자동 생성 / 수정할 때 증가 |
| name / kind | 에셋 이름 / image 또는 sound |
| group / usage | 자유로운 하위 분류 / 어느 상황에 어떻게 쓰는지, usage는 필수 |
| usage_state | planned: 적용 예정 / in_use: 사용 중 / unused: 미사용 |
| status | temporary: 임시 / proposed: 제안 / confirmed: 확정 / retired: 사용 종료 |
| methods | code / image_skill / external / other_skill 배열. 복수 가능 |
| files | 프로젝트 내부 파일·구현 코드의 상대 경로 배열. 적용 전이면 빈 배열 가능 |
| art_notes | 공통 아트 기준을 해당 에셋에 적용하는 구체적 제작 조건 |
| reason | 제작 방식과 현재 결과를 선택한 이유. 혼합할 경우 혼합 이유 포함, 필수 |
| source_note | 코드 내 위치, 실제 사용 도구·스킬과 생성 조건, 외부 출처 등 추적에 필요한 정보 |
| replacement_plan | 임시물의 교체 대상·시점·기준. temporary일 때 필수 |
| decision_ids / reference_ids | 같은 프로젝트의 사용자 결정 ID / 레퍼런스 ID 배열 |
| approval_quote | 확정 선택의 사용자 원문. 새 확정이나 아트 변경 후 확정 시 필수 |
| change_note | 이번 등록·수정 이유. 이력에 저장, 필수 |

other_skill은 제작 방식의 기록값이다. 연결되지 않은 스킬을 실행할 수 있다고 보고하지 않는다. image_skill도 실제 사용한 이미지 생성 도구를 source_note에 적는다.

## 명령

AGENTS.md의 Python·결정 명령 경로를 사용한다. 아래는 그 명령 뒤에 붙이는 인자다. add/update는 UTF-8 JSON 파일 또는 stdin을 받는다. DB를 직접 편집하지 않는다.

```text
asset add --input asset-input.json
asset list --kind image --status temporary
asset list --query "찾을 용도나 이름"
asset show A-001
asset update A-001 --revision 1 --input asset-update.json
asset history A-001
```

add의 필수 필드는 name, kind, usage, methods, reason, change_note다. 기본 상태는 temporary이므로 replacement_plan도 입력한다. update는 변경 필드와 change_note만 보낼 수 있다. 조회한 revision을 사용하며 충돌 시 최신 기록을 읽고 사용자 변경을 반영한다. 무조건 덮어쓰지 않는다.

대시보드의 에셋 수정 요청은 해당 에셋의 ID·버전·기록과 사용자 원문을 함께 전달한다. 수정 후 같은 ID의 기록과 실제 적용 상태를 갱신한다. 단순 파일 업로드·경로 변경은 게임 코드 적용 완료를 뜻하지 않는다.
