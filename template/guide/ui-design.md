# 게임 UI 설계와 승인 기준

## 적용 범위와 역할

- 게임 UI의 방향을 정하거나 대표 화면을 만들 때 적용한다. 승인된 방향 안의 수치·오탈자 수정에 전체 설계 절차를 반복하지 않는다. 처음 필요한 단계의 절만 읽고, 같은 컨텍스트의 기준은 재사용한다.
- 오케스트레이터는 ‘방향과 사용자 확인’, ‘대표 화면과 승인’, ‘기록과 후속 전달’을 사용해 배정·사용자 선택·기록을 연결한다. 실무 담당의 다른 지침을 대신 읽지 않는다.
- 게임 디자이너는 플레이어의 판단·조작에 필요한 정보, 중요도, 표시 상황과 화면 흐름을 설계한다. 새 화풍·세계관·스토리를 대신 정하지 않는다.
- 레퍼런스 담당은 사용자가 고른 참고 요소의 관찰·해석 근거를 반환한다. 아트 담당은 관련 에셋의 제작 조건·일관성과 버전을 관리한다. 아트 담당에게 화면 배치나 조작 검증을 맡기지 않는다.
- 개발 담당은 UI 설계가 배정되면 승인된 화풍과 정보 설계 안에서 배치·글자·색의 역할·상태 표현을 구체화한 안을 오케스트레이터에게 반환하고, 선택된 방향으로 대표 화면과 공통 UI를 구현한다. UI 설계를 맡았다는 이유로 새 화풍이나 에셋을 확정하지 않는다. 검증 담당은 승인된 기준과 실제 표시·조작의 일치를 확인하며 미적 취향을 결정하지 않는다.
- 담당 수만큼 에이전트를 실행하거나 새 역할을 만들지 않는다. 해당 작업에 필요한 담당만 사용하며, 사용자 대화는 오케스트레이터가 맡는다.

## 방향과 사용자 확인

- 기존 `ui_style`, `art_style`, `color_palette`, `viewpoint`, `platform` 결정 중 이번 화면과 관련된 topic부터 확인한다. 확정된 것을 다시 묻지 않는다. 화풍이 정해졌다는 이유로 UI 배치·정보 밀도·글꼴·상호작용까지 정해졌다고 취급하지 않는다.
- UI의 출발점은 해당 게임에서 플레이어가 무엇을 보고 판단하고 조작하는지다. 중요한 정보와 보조 정보, 상시 표시와 상황별 표시, 주요 행동과 그 결과를 구분한다. 기존 정보·피드백 설계가 있으면 재사용한다.
- 모양을 선택할 때는 게임의 승인된 시각 방향과 정보의 역할에 연결한다. ‘깔끔하게’, ‘고급스럽게’, ‘AI스럽지 않게’ 같은 형용사만 제작 기준으로 전달하지 않는다. 색의 역할, 글자 크기 차이, 간격·정렬, 패널·버튼 형태, 선택·눌림·비활성 상태 등 이번 화면에 필요한 선택으로 구체화한다.
- 카드·그라데이션·둥근 모서리·특정 글꼴을 일괄 금지하지 않는다. 익숙한 웹 대시보드 양식을 게임에 자동 적용하거나 차별화를 위해 무관한 장식을 추가하지 않는다. 해당 형태가 정보 구분·조작·승인된 표현 의도 중 무엇에 필요한지 설명할 수 있어야 한다.
- 사용자가 세부 선택을 원하면 중요한 차이가 보이는 후보를 기존 질문 규칙으로 제시한다. 판단을 맡기면 AI가 일관된 한 안을 만들어 보여주고 `proposed`로 기록한다. 색·간격·테두리 하나마다 질문하지 않는다. 이미 승인한 화면이나 사용자가 직접 지정한 기준이 있으면 후보 제작·방향 승인을 반복하지 않는다.
- 사용자 방향은 기존 topic인 `ui_style`의 `UI 스타일`, `HUD 구성`, `메뉴 구성`, `글꼴과 글자 크기` 등과 `color_palette`의 해당 topic에 저장한다. 한 묶음을 승인받아도 항목별 기록과 기존 번복 규칙을 따른다. 이 문서를 읽었다는 이유로 topic이나 빈 결정 기록을 추가하지 않는다.

## 레퍼런스에서 화면 규칙으로

- 레퍼런스의 이름이나 ‘이런 느낌’만 구현 지시로 넘기지 않는다. [레퍼런스 추적 기록](reference-tracing.md)의 기존 research → interpretation → application 흐름을 사용한다. 참고 자료가 없으면 조사 결과나 근거 ID를 만들지 않는다.
- 실제 확인한 이미지·화면·영상 구간을 사용자에게 보여주고, 사용자가 고른 요소를 우리 게임의 화면 규칙으로 어떻게 옮길지 설명한다. 관찰 사실, AI의 해석, 적용 제안과 원본과의 차이를 구분한다. 이미 확인한 참고 요소를 다시 묻지 않는다.
- 관찰은 배치, 정보별 크기 차이, 여백·정보 밀도, 글자·테두리·색의 역할, 입력에 대한 반응처럼 확인 가능한 내용으로 남긴다. 정지 이미지에서 알 수 없는 동작·시간·전환은 관찰했다고 쓰지 않는다.
- 예를 들어 레퍼런스에서 ‘중요 수치가 가장 크게 보인다’를 관찰했다면 우리 게임에서 어떤 수치를 어떤 크기 관계로 보여줄지 제안한다. 원본의 기능·에셋·화면 전체를 함께 가져오지 않는다. 기존 레퍼런스의 사용 범위와 복제 금지 규칙을 따른다.

## 대표 화면과 승인

- 승인된 개발 범위 안에서 UI 방향의 차이를 확인할 수 있는 실제 게임 화면 하나부터 만든다. 원래 필요한 화면을 대표로 고르며 별도 데모나 소개 페이지를 추가하지 않는다. 성격이 다른 화면까지 이 한 화면으로 승인받았다고 확대하지 않는다.
- 첫 핵심 루프의 도형·텍스트 구현은 기능 확인용이다. 그 모습을 최종 UI로 간주하지 않는다. 해당 UI를 여러 화면으로 확장하기 전에 대표 화면을 기존 마일스톤의 사용자 확인 지점에 포함한다. 기능 단위마다 별도 승인 절차를 만들지 않는다.
- 대표 화면에는 실제 프로젝트의 문구·수치·콘텐츠와 필요한 조작 상태를 사용한다. 보기 좋게 채운 임의의 카드·슬로건·가짜 통계로 시안을 꾸미지 않는다. 결과를 좌우하는 에셋은 이 단계에서 먼저 적용할 수 있다. 미완성 부분은 임시 에셋으로 기록하고 승인 대상에서 빠진 부분을 함께 알린다.
- 사용자에게 실제 렌더링된 화면 캡처, 직접 열어 볼 경로, 확인 대상 상태·화면 크기와 이번 선택의 이유를 짧게 제시한다. HTML·CSS 값이나 이미지 생성으로 만든 목업만 보여주고 실제 게임 화면을 확인받았다고 하지 않는다. 캡처를 못 했으면 그 사실과 실행 경로를 알리고 화면을 봤다고 기록하지 않는다.
- 사용자 선택은 기존 질문 도구로 받는다. 일부 수정이면 영향받는 부분을 고쳐 보여주고, 나머지 합의 내용은 유지한다. 방향을 위임받은 것, 기능이 동작하는 것, 검증 통과는 화면 승인으로 바꾸지 않는다. 기존 승인·직접 지정이 이번 화면과 범위를 이미 포함하면 다시 승인받지 않는다.
- 승인 전에도 그 선택과 무관한 승인된 작업은 진행할 수 있다. 승인받지 않은 시각 방향을 여러 화면의 최종 기준으로 확장하지 않는다. 승인은 대상 화면·상태와 공통 규칙에 한정하며 게임 전체의 만족을 뜻하지 않는다.

## 기록과 후속 전달

- 기준의 원본은 프로젝트의 `design/ui/v001/`, `v002/`처럼 버전별 폴더에 둔다. 한 버전의 `baseline.md`에는 아래 내용을 담고 실제 캡처도 같은 폴더에 둔다. 사용자가 확인한 파일은 덮어쓰지 않고 바뀐 안은 다음 버전으로 만든다. 기존 프로젝트에 같은 목적의 버전 관리 문서가 있으면 그 위치를 사용하고 중복 원본을 만들지 않는다.

| 기준에 남길 내용 | 기록 범위 |
|---|---|
| 적용 대상 | SPEC 버전, 화면·상태, 대상 플랫폼·입력·크기, 이번 승인에 포함되지 않는 임시 부분 |
| 설계 이유 | 플레이어의 판단·조작, 정보의 우선순위, 선택한 시각 방향과 그 이유 |
| 표현 규칙 | 실제 선택한 색의 역할·값, 글꼴·크기 관계, 간격·정렬, 패널·버튼 형태와 상태별 표현. 필요하지 않은 항목은 추가하지 않음 |
| 근거 | 관련 사용자 결정 U-ID, 레퍼런스 R-ID와 해석 RT-ID, 구현 선택 W-ID. 없는 근거는 만들지 않음 |
| 실제 결과 | 화면 캡처 상대 경로, 실행 진입점과 재현할 상태, 관련 에셋 A-ID·revision, 구현 파일과 공통 스타일·문구 데이터 위치 |

- `baseline.md`와 승인 대상 캡처를 저장한 뒤 그 파일의 SHA-256을 구한다. 제안·승인 기록의 `decision`에 기준 버전·상대 경로·해시·적용 범위를 포함하고 `reference_ids`에는 실제 사용한 R-ID만 연결한다. 해시는 승인받은 파일을 식별하는 용도이며 미적 품질 점수가 아니다.
- 대표 화면과 공통 UI 방향의 제안·승인은 `category=ui_style`, `topic=UI 스타일`의 사용자 결정으로 기록한다. 기존 UI 스타일을 구체화하거나 변경할 때는 유지할 내용과 변경 내용을 포함하고 `supersedes` 규칙을 따른다. 승인 원문과 AI 답변은 기존 규칙대로 보존한다. 다른 topic까지 변경하면 해당 항목도 따로 기록한다.
- 승인 상태의 원본은 DB의 `user_decisions.status`다. `baseline.md`의 제목이나 폴더명, 작업 결정의 active, 에셋의 적용 여부로 승인을 추정하지 않는다. 방향·승인에 관한 사용자 결정을 작업 결정에 중복 저장하지 않는다. 공통 스타일 구조와 적용 방식 같은 구현 선택은 `work_decisions`의 `area=ui` 등 실제 영역에 기록한다.
- 오케스트레이터는 STATE.md의 20줄 제한 안에서 현재 기준의 사용자 결정 ID와 경로를 남긴다. UI 작업 배정에는 해당 기준 버전·경로·관련 캡처와 이번 적용 범위를 전달한다. 담당은 그 기준의 필요한 부분을 직접 읽고 이미 읽은 동일 버전은 재사용한다. 전체 레퍼런스와 기록을 매 작업마다 다시 읽지 않는다.
- 변경은 기존 번복 절차를 사용한다. 새 기준과 영향받는 화면을 연결하고, 채택하지 않은 후보는 선택되지 않은 이유·파일 경로와 함께 오케스트레이터에게 반환한다. 파일을 임의로 삭제하지 않는다. 폐기용 위치는 AGENTS.md를 따른다.

## 후속 구현과 확인

- 개발 담당은 승인된 공통 스타일·컴포넌트·문구 저장 방식을 재사용한다. 같은 역할의 버튼·수치·패널을 화면마다 새로 디자인하지 않는다. 다른 표현이 필요한 경우 정보의 역할과 기존 기준의 부족한 점을 근거로 정리하고, 방향 변경이면 오케스트레이터에게 반환한다.
- 검증 담당은 이번 변경에 관련된 기준 화면·규칙·상태만 실제 화면과 비교한다. 정보의 우선순위, 선택 상태의 구분, 공통 표현, 잘림·겹침·조작을 해당 완료 조건 안에서 확인한다. 캡처 픽셀의 완전 일치나 ‘AI 느낌 점수’를 통과 조건으로 만들지 않는다.
- ‘예쁜가’, ‘개성이 있는가’, ‘마음에 드는가’는 사용자 평가다. 검증 통과는 승인된 기준과 동작·표시가 맞는지 확인한 결과로만 보고한다. 사용자 평가가 없는 취향을 검증 담당이 보충하지 않는다. 확인 범위·반복 한도는 검증 담당의 기존 지침을 그대로 따른다.
